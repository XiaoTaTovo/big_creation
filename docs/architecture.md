# 系统架构草案

状态：Draft 0.1

本文给出便于讨论和原型验证的建议架构，不代表已冻结的硬件方案。

## 1. 总体数据流

```text
USB-C CC1/CC2
    │
    ▼
保护与模拟前端 / PD PHY
    │  原始符号、边沿或已恢复数据
    ▼
采集与时间戳模块
    │  CaptureRecord
    ▼
有界环形缓冲区 / 核间消息通道
    │
    ▼
帧恢复与协议解析
    │  PdFrame / PdEvent
    ├──────────────► 日志与外部导出
    ▼
协商状态归纳
    │
    ▼
嵌入式 GUI
```

核心原则：**采集路径不等待界面，界面不接触硬件采集细节。**

## 2. 建议的任务划分

### 实时侧

- 接收中断/DMA/PHY 数据；
- 记录方向、通道、时间戳和原始长度；
- 做必要且有界的帧边界判断；
- 将记录写入预分配缓冲区；
- 统计溢出、丢帧和硬件错误；
- 禁止动态内存分配、复杂格式化输出和 GUI 调用。

### 处理与展示侧

- 从缓冲区读取并恢复完整帧；
- 校验 CRC，解析 Header 和 Data Objects；
- 将报文转为稳定的中间数据模型；
- 维护协商状态摘要；
- 更新 GUI，并按需导出到 PC；
- 在负载过高时允许降低界面刷新率，但不能反向阻塞采集。

双核是否分别承担上述两侧，应由 CH32H417 的实际核间通信、内存一致性和外设归属验证决定；在冻结前不要把业务代码绑定到某个核号。

## 3. 模块边界

建议固件至少拆分为以下模块：

- `bsp`：时钟、引脚、中断、缓存一致性、板级初始化；
- `drivers`：显示、触摸、存储、串口/USB、PD 前端接口；
- `capture`：原始采集、时间戳、缓冲区和丢帧统计；
- `pd_codec`：BMC/4b5b/帧恢复等与具体方案相关的编解码；
- `pd_protocol`：消息头、控制消息、数据消息、扩展消息和 CRC；
- `pd_session`：协商过程和关键事件归纳；
- `ui_model`：面向 GUI 的不可变快照或事件队列；
- `ui`：页面、控件、筛选、详情和性能统计；
- `export`：串口/USB 日志格式与上位机协议；
- `platform`：RTOS/裸机抽象和核间通信封装。

协议解析模块应尽量不依赖 MCU 寄存器和 GUI，以便同一份代码在 PC 测试程序中运行。

## 4. 中间数据模型

建议先定义稳定的数据对象，再分别实现采集和界面：

```text
CaptureRecord
- timestamp
- cc_line
- direction_or_role_hint
- raw_length
- raw_payload/reference
- capture_flags

PdFrame
- timestamp
- sop_type
- spec_revision
- power_role / data_role
- message_id
- message_type
- data_object_count
- crc_status
- decoded_objects[]
- parser_warnings[]

PdEvent
- timestamp
- event_type
- short_summary
- related_frame_ids[]
```

具体字段需以正式 USB PD 规范和目标版本为准，避免直接照抄某个开源项目的数据结构。

## 5. 缓冲与背压

- 所有队列必须有固定容量和可观察的溢出计数。
- GUI 仅保留最近 N 条或分页快照，不能无限保存对象。
- 原始数据、解析帧和显示文本应分层保存，避免重复复制大块内存。
- 导出速度不足时，优先丢弃非关键显示日志或停止导出；不能阻塞采集 ISR。
- 对跨核共享数据明确使用单生产者/单消费者队列、临界区或经验证的原子操作。

## 6. 首轮架构验证

在 PCB 定版和 GUI 大规模开发前，至少完成：

1. 用固定输入验证采集到解析的吞吐上限；
2. 验证缓存溢出时系统可继续运行且能报告丢帧；
3. 验证解析器在 PC 与 MCU 上对同一测试向量输出一致；
4. 验证界面刷新不会改变采集结果；
5. 记录 RAM、Flash、CPU 占用和最坏处理延迟；
6. 对未知、截断、CRC 错误报文进行容错测试。
