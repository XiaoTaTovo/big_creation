# 0. 先看这一页：我们到底要做什么？

## 0.1 一句话理解项目

**PD Insight 是一台串在充电器与手机之间、尽量不影响原有充电过程、监听 USB-C CC 线路上的 USB PD 协商消息，并将它们解析成时间线、字段详情和供电协商摘要显示在屏幕上的便携式协议分析仪。**

最通俗的比喻：

> 它是 USB 快充对话的 **录音机 + 翻译器 + 字幕机 + 回放工具**。

它的核心价值不是“测一下几伏几安”，而是：

> **把看不见的快充协商过程变得可见。**

---

## 0.2 它和普通 USB 功率表有什么区别？

普通功率表主要回答：

- 现在实际多少 V？
- 现在实际多少 A？
- 现在实际多少 W？
- 累计多少 Wh？

PD Insight 更主要回答：

- 充电器宣称支持哪些供电档位？
- 手机请求了哪个档位？
- 充电器是否接受？
- 当前建立了什么供电合同？
- 中间传输了哪些 USB PD 报文？
- CRC 是否正确？
- 有无丢帧、异常、重置等事件？

例如：

```text
00.000 ms  充电器 -> 手机  Source_Capabilities
                         5V/3A, 9V/3A, 15V/2A

02.310 ms  手机 -> 充电器  Request
                         请求 9V/2A

02.800 ms  充电器 -> 手机  Accept

05.400 ms  充电器 -> 手机  PS_RDY
```

界面可总结成：

```text
连接成功
CC 通道：CC1
供电方：Source
用电方：Sink
可用档位：5V / 9V / 15V
请求：9V / 2A
协商结果：成功
CRC Error：0
```

# 1. 当前项目边界与产品形态

## 1.1 推荐的首版产品形态

```text
墙上插座
   |
 充电器
   |
   | USB-C
   v
+-----------------------+
| PD Insight 分析仪     |
|                       |
| Type-C 输入            |
| Type-C 输出            |
| CH32H417 主控          |
| 屏幕 + 触摸            |
+-----------------------+
   |
   | USB-C
   v
 手机 / Sink
```

推荐首版原则：

- 物理上：在充电器和手机之间
- 供电上：透明透传
- 协议上：被动监听
- 显示上：解析和总结
- 首版不主动修改报文
- 首版不主动控制充电器
- 首版不做攻击/故障注入
- 首版不做 USB 2.0/3.x 高速数据内容分析
- 首版不做工业级 USB-IF 一致性认证

---

## 1.2 “分析仪在中间”不等于“电流经过 MCU”

这一点必须牢牢记住：

```text
                    +---- CH32H417 ---- 屏幕
                    |
                    | 只监听 CC
                    |
充电器 ==== VBUS ===================== 手机
       ==== GND  =====================
       <------ CC 通信 -------------->
```

**手机充电的几安培大电流不经过 CH32H417 芯片。**

MCU 更像路边摄像头，不是高速公路本身。

# 2. USB Type-C / USB PD 最基础的物理理解

## 2.1 两条最重要的“路”

### VBUS / GND
负责真正搬运电能。

```text
充电器 ======== VBUS / GND ======== 手机
```

### CC
负责：

- 连接检测
- 正反插判断
- Source / Sink 角色识别
- Rp / Rd
- USB PD 通信
- 部分 VCONN 相关逻辑

```text
充电器 <========= CC =========> 手机
```

---

## 2.2 记住这个比喻

| USB PD 概念 | 比喻 |
|---|---|
| Source | 餐厅 |
| Sink | 顾客 |
| Source_Capabilities | 菜单 |
| PDO | 菜单中的一道供电档位 |
| Request / RDO | 顾客点餐 |
| Accept | 餐厅同意 |
| PS_RDY | 菜做好，可以开始 |
| VBUS | 真正送餐/送电的道路 |
| CC | 双方打电话协商的线路 |

# 4. 双核到底怎么理解？

## 4.1 最通俗的模型

把 CH32H417 想成一颗芯片里放了两个 CPU 工人。

```text
CH32H417
+-----------------------------------+
|                                   |
| V3F 核               V5F 核       |
|                                   |
| 实时采集             解析 + GUI   |
| 时间戳               数据整理     |
| DMA/中断             LVGL         |
|                                   |
|       <--- 共享 SRAM / 队列 --->   |
+-----------------------------------+
```

推荐的架构思想：

### 实时侧
负责：

- CC / PD PHY 数据接收
- 中断 / DMA
- 时间戳
- 原始记录
- 丢帧统计
- 快速写入固定缓冲区

要求：

> 快、短、不能被 GUI 卡住。

### 处理和显示侧
负责：

- 读取采集记录
- 帧恢复
- CRC
- Header / Data Object 解析
- 协商状态总结
- LVGL GUI
- PC 导出

要求：

> 可以慢一点，但绝不能反向阻塞采集。

---

## 4.2 双核之间怎么传数据？

推荐：

**SPSC Ring Buffer**

SPSC：

> Single Producer Single Consumer  
> 单生产者 / 单消费者

```text
V3F 生产
  |
  v
+-------------------+
| Ring Buffer       |
| CaptureRecord     |
| CaptureRecord     |
| CaptureRecord     |
+-------------------+
  |
  v
V5F 消费
```

以后需要学习：

- Shared Memory
- Ring Buffer
- HSEM
- Memory Barrier
- Cache Consistency
- Ownership
- Interrupt Notification

但这些都不应该在最初阶段一次性全学。

# 5. GUI 最终怎么构建？

## 5.1 推荐硬件路线

当前使用官方 CH32H417QEU-R0-1v1 评估板：

```text
CH32H417
   |
   +-- LTDC RGB565 ---> RGB LCD
   |
   +-- I2C -----------> Touch Controller
   |
   +-- FMC -----------> SDRAM
                           |
                           +-- Frame Buffer
```

重点：

> **屏幕本体走 LTDC RGB 并行接口。**  
> **I²C 主要用于电容触摸，不是拿来传整屏像素。**

---

## 5.2 为什么不用 I²C 刷屏？

I²C 适合：

```text
Touch X = 215
Touch Y = 93
Pressed = 1
```

不适合不断传：

```text
像素1
像素2
像素3
...
一整屏像素
```

---

## 5.3 SPI 和串口屏是什么定位？

### SPI 屏
优点：

- 接线少
- 驱动相对简单
- 小屏常用

问题：

- 大尺寸高刷新率 GUI 带宽压力明显

### 串口屏
结构：

```text
CH32 -- UART --> 智能屏
```

优点：

- 开发快

问题：

- GUI 真正渲染工作跑到屏幕厂商 MCU
- 对“嵌入式界面实现”的研究价值偏低
- 不利于深入掌握 LTDC / SDRAM / LVGL

所以本项目更建议：

> **LTDC RGB LCD + I²C Touch + SDRAM + LVGL**

# 6. 电流怎么安全通过？为什么不会把 MCU 烧掉？

## 6.1 大电流 Power Path 和 MCU 必须分开

### Power Path

```text
USB-C IN
   |
   | VBUS
   v
粗铜箔 / 铜面
   |
   v
USB-C OUT
```

真正的大电流主要经过：

- Type-C 连接器
- PCB 铜箔
- 过孔
- 可能的 MOSFET
- eFuse
- 采样电阻
- 保护器件

而不是经过 MCU。

---

## 6.2 监听 Path

```text
CC1 / CC2
   |
   +----> 保护 / 模拟前端
                |
                v
            PD PHY
                |
                v
            CH32H417
```

监听电路目标：

> 能看到 CC 信号，但尽量不改变原有 Source <-> Sink 协商。

需要避免：

- 额外错误的 Rp
- 额外错误的 Rd
- 输入阻抗太低
- 保护器件引入过大电容
- 线路寄生导致 CC 波形失真

---

## 6.3 真正危险的是什么？

例如：

```text
20V VBUS
   |
   +--------误接-------> 3.3V MCU GPIO
                           |
                           +--> 烧毁
```

危险的核心不是：

> “手机 3A 电流灌进 MCU”

而是：

> **高电压 / 大电流走错路径。**

---

## 6.4 早期真实测试安全路线

不要一开始：

```text
100W 充电器
   |
第一次焊的 PCB
   |
昂贵手机
```

正确顺序：

```text
阶段 1
固定假报文
-> PC
-> 协议解析
-> GUI

阶段 2
CH32 开发板
-> 官方例程
-> 基本外设验证

阶段 3
5V / 限流电源
-> 透传板
-> 电子负载

阶段 4
普通 5V 充电器
-> 透传板
-> 受控 Sink

阶段 5
验证压降 / 温升 / CC 监听

阶段 6
逐渐测试 9V / 12V / 15V / 20V 等 SPR 场景

最后
再考虑 PPS / EPR / 高功率
```

## Stage 2：Timer + Interrupt + DMA

### Timer

理解：

> CPU 不用自己一直数时间，硬件 Timer 可以独立计时。

实验：

- 1 ms tick
- 定时切换 LED

### Interrupt

理解：

```text
CPU 正在运行
    |
事件发生
    |
    v
ISR
    |
返回原流程
```

必须形成项目铁律：

> **PD 实时采集 ISR 中绝不能直接画 GUI。**

### DMA

理解：

没有 DMA：

```text
CPU 自己搬字节
```

有 DMA：

```text
CPU：
“DMA，把这批数据搬到 RAM。”

DMA：
“收到。”

CPU：
继续做别的。

DMA 完成：
中断通知 CPU
```

最终你要理解：

```text
外设
 |
DMA
 |
RAM
```

这就是以后：

```text
PD PHY
 |
DMA / ISR
 |
Capture Buffer
```

的基础。
